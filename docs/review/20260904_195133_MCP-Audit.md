# Независимый аудит MCP HZR для агентской работы

Дата: 2026-09-04, Europe/Moscow.
Source HEAD: `fbf204d48704160407e3f06035ac32b9cf0bc67a` (HZR 0.7.1).

Это новый внутренний reviewer memo по текущим исходникам и свежему MCP handshake/tools-list. Предыдущие PRD не использовались. Аудит выполнен отдельным субагентом по прямому запросу пользователя. Код и конфигурация не менялись.

## Статус доказательств

- **Code-proven**: поведение выведено из прочитанных текущих исходников; конкретные места перечислены ниже.
- **Measured**: размер свежего JSON tools/list из `/tmp/hzr-audit-20260904/mcp-probe.jsonl`.
- **Not exercised**: реальный host transcript, provider billing, полный сценарий cancellation и mutating MCP calls не проверялись этим субагентом. Большой suite выполняется основным агентом; этот memo не объявляет его результат.
- Попытка дополнительного Python subprocess MCP probe была отклонена HZR policy: `exit 77`, `T2 Ask E3`, interpreter file read. Обход не выполнялся. Это не доказательство отсутствия безопасного MCP test route: основной агент располагает работающим NDJSON/heredoc probe через HZR.

## Вердикт

MCP имеет хорошую основу безопасности и типизации, но наличие 13 tools не означает полноту эффективного агентского workflow. Недоработаны обычное редактирование, управляемое дочитывание, бюджет повторных запросов и длительное выполнение. Текущая поверхность способна вынуждать модель обращаться к CLI/native операциям даже для штатных задач.

Оптимизировать нужно полную задачу при сохранении качества, а не процент сокращения каждого ответа. Одна полная загрузка обоснованного файла может быть дешевле outline, нескольких ranges, повторных запросов и потери связного контекста.

## P1: MCP write отвергает удаление блока и пустые файлы

**Code-proven.** `crates/hzr-cli/src/mcp/tools.rs:919` публикует `old`, `new`, `content` без запрета пустой строки. Однако `write_fork_request` в `crates/hzr-cli/src/mcp.rs:1196` и `:1207` вызывает `bounded_required_string` (`:1226`), который использует `required_string` из `crates/hzr-cli/src/mcp/arguments.rs:75`. Последний отвергает `value.trim().is_empty()`.

Последствия:

- `new:""` нельзя использовать для удаления найденного блока;
- замена на whitespace-only строку невозможна;
- пустой файл через `create content:""` не создаётся;
- schema-valid запрос отклоняется parser до daemon execution.

Безопасный пример запроса для последующего подтверждения:

```json
{"name":"hzr_write","arguments":{"operation":"patch","path":"__audit_nonexistent__","old":"remove me","new":""}}
```

По коду ожидается `argument new must not be empty`; файл не должен затрагиваться. В рамках этого memo запрос не выполнялся.

**Требование:** отделить непустые идентификаторы/path от произвольного exact content. `new` и `content` должны сохранять пустые и whitespace строки. Добавить реальные parser/end-to-end regression tests удаления, пустого create и whitespace replacement.

## P1: нет полноценного MCP-контракта дочитывания

**Code-proven.** `hzr_read` экспонирует только `path`, `outline`, `from`, `to`, `max_lines` (`crates/hzr-cli/src/mcp/tools.rs:884`; `crates/hzr-cli/src/mcp.rs:1141`). Существующие CLI batch и общий `max_tokens` недоступны. Нет нескольких ranges в одном запросе, symbol selection, content-reference expansion и snapshot/hash для следующего чтения.

Полное чтение технически возможно через явный диапазон или `max_lines`: `fork-core/rtk/src/main.rs:2144` выбирает `FilterLevel::None` для таких запросов. Поэтому утверждать, что MCP вообще не способен вернуть полный файл, неверно. Проблема в отсутствии явного полезного выбора и в необходимости самостоятельно узнавать размер, помнить предыдущие spans и склеивать ranges.

`stdout_truncated` отражает усечение transport capture, а не полноту исходного файла:

- `crates/hzr-daemon/src/api.rs:2697`: capture ограничен 192 KiB;
- `fork-core/rtk/src/read.rs:330` и `:354`: ограничение исходного чтения сообщается человекочитаемыми notices;
- `crates/hzr-cli/src/mcp.rs:1247`: MCP wrapper переносит stdout и transport flags.

`stdout_truncated:false` может сопровождать неполный файл. Recovery notices существуют; нельзя утверждать, что пропуски полностью скрыты. Но LLM должна разбирать human text вместо typed completeness.

**Требование:** развить `hzr_read` параметрами `mode:auto|exact|outline`, `max_tokens`, paths/ranges batch. Возвращать `source_hash`, `total_lines`, `shown_ranges`, `omitted_ranges`, `complete`, `next_cursor`. Cursor должен быть привязан к workspace и source hash. Разрешать один full exact read, если он дешевле ожидаемой цепочки фрагментов.

## P1: retrieval не выражает бюджет текущей задачи

**Code-proven.** `hzr_context_plan` принимает intent/path/search_limit/memory_limit/topic, но не token budget (`crates/hzr-cli/src/mcp.rs:1093`). Планировщик берёт configured hard limit (`crates/hzr-context/src/planner.rs:142`). Search ограничивает число hits, а не общий размер ответа; нет cursor/offset и already-seen spans. Memory recall ограничивает count, а не бюджет доставки.

Повторные вызовы могут снова выдавать уже увиденные материалы. Внутренний dedup одного context plan не доказывает dedup между агентскими шагами.

**Требование:** per-request budget и opt-in task context/snapshot; помнить доставленные exact spans и поддерживать explicit refresh. Выбор маршрута должен учитывать цену дополнительного вызова, повторного контекста и вероятность последующего expansion. Не подменять эту задачу запретом full read.

**Приёмка:** task-level A/B evals с одинаковыми заданиями и качеством результата: total model-visible tokens, число reads/retries, latency, успешность исправления. Уменьшение одного stdout не является успешным итогом, если вся задача стала дороже.

## P1: длительные команды не имеют полноценного MCP workflow

**Code-proven.** `hzr_exec` ограничивает `timeout_ms <= 29500` (`crates/hzr-cli/src/mcp.rs:1106`). Нет operation handle, poll/wait, stdin, execution cancel и recovery artifact. Progress notifications реализованы только для search/context (`crates/hzr-cli/src/mcp.rs:314`).

MCP cancellation вызывает `AbortHandle.abort()` у клиентского call future (`crates/hzr-cli/src/mcp.rs:270`); daemon API requests не несут operation ID/cancellation token (`crates/hzr-protocol/src/api.rs:275`, `:699`). Это доказывает отсутствие явного end-to-end cancellation-протокола, но не доказывает, что любой отменённый вызов оставляет процесс. Последнее требует integration test.

**Требование:** start → operation_id → wait(cursor) → cancel; длительность операции не должна ограничиваться одним transport wait. Повторное ожидание не должно повторно запускать команду. Проверить отмену до dispatch, во время исполнения, после завершения и при разрыве MCP/HTTP.

## P2: schema и фактический parser расходятся

**Code-proven.**

- `from/to/max_lines` публикуются без maximum (`crates/hzr-cli/src/mcp/tools.rs:896`), но runtime parser ограничивает их `100_000` (`crates/hzr-cli/src/mcp.rs:1156`).
- JSON Schema `maxLength` считается в Unicode characters (`crates/hzr-cli/src/mcp/tools.rs:1088`), но `bounded_required_string` ограничивает UTF-8 bytes (`crates/hzr-cli/src/mcp.rs:1228`). Schema-valid кириллическая строка может нарушать runtime byte limit.
- Пустые `new` и `content` дают отдельное расхождение, описанное выше.

Тест `acceptance_gate_advertised_input_schema_is_the_runtime_parser_contract` (`crates/hzr-cli/src/mcp/tools.rs:1213`) проверяет schema validator, unknown/wrong-type/required fields, но не вызывает runtime parser. Название шире фактического покрытия.

**Требование:** единая typed модель аргументов и генерируемая схема; byte limits отражать явно. Один corpus boundary/Unicode inputs должен прогоняться и через schema validation, и через parser.

## P2: учёт не представляет фактическую стоимость MCP-доставки

**Code-proven.** `tool_success` (`crates/hzr-cli/src/mcp.rs:1395`) помещает полный result в `content[0].text` как JSON string и в `structuredContent` как object. `mcp_operation_request` (`:785`) считает только внутренний JSON result через `len()/4`.

В этой оценке отсутствуют внешняя envelope, JSON escaping, tool arguments, schema exposure, recovery follow-ups и host rendering. Дублирование structured/text может быть оправдано совместимостью MCP; нельзя автоматически объявлять двукратную модельную стоимость, потому что host может выбрать один канал. Текущий ledger этого не измеряет.

**Measured.** Свежий tools/list содержит 13 definitions. Compact JSON массива definitions занимает **25 574 UTF-8 bytes**; result `{"tools":...}` — **25 584 bytes**. Это размер wire JSON, не tokenizer measurement и не provider billing. Тест `25 * 1024` bytes (`crates/hzr-cli/src/mcp/tools.rs:1313`) оставляет 16 bytes запаса. Его комментарий о 23 776 bytes устарел относительно этого snapshot.

Не смешивать эту метрику с размером отдельных descriptions, autogenerated host tool declarations или общего host instructions prefix: они относятся к другим слоям доставки.

**Требование:** исследовать фактически видимый transcript отдельно для каждого host. Сохранить structured output для машинной обработки, а модельное представление сделать компактным там, где host позволяет. Provider usage и estimates отчётливо разделять; учитывать arguments/results/retries/recovery и schema exposure на уровне полной задачи.

## P2: часть typed outputs непрозрачна для LLM

**Code-proven по текущему tools/list.** `hzr_exec.result` и `disposition`, `hzr_write.receipt` объявлены просто object. Doctor содержит массивы произвольных объектов. Это не нарушение типизации Rust, но LLM не видит статусов и recovery fields в schema.

**Требование:** компактные discriminated shapes для решений агента. Подробную диагностику отдавать по запросу. Не разворачивать все внутренние Rust структуры в постоянно загружаемую schema без измерения стоимости.

## Что сохранять

- Единый registry 13 tools, строгие `additionalProperties:false`, runtime validation inputs/outputs.
- Проверку workspace binding и отказ при конфликте pinned workspace/client root.
- Отсутствие скрытого fallback store и проверку namespace ownership.
- Project scope по умолчанию, prune dry-run, CAS write и daemon confinement.
- Явные degraded search modes, provenance/context warnings.
- Честное указание, что codec не подтверждает замену final response.
- Transport hashes/termination, дополненные отдельной полнотой исходного содержимого.

## Критерии завершения улучшения MCP

1. Delete-block, empty-create и whitespace patch выполняются через MCP без shell обхода.
2. Full read, ranges и batch сравниваются на одинаковых задачах; default не увеличивает total task tokens ради меньшего отдельного ответа.
3. Expansion не возвращает уже доставленные spans без причины; изменение source инвалидирует cursor.
4. Команда дольше 30 секунд завершается через start/wait без повторного запуска.
5. JSON Schema и runtime parser совпадают на boundary/Unicode corpus.
6. Измерение охватывает реально видимые host definitions, arguments, results, retries и recovery.
7. Schema byte cap, passed unit tests и локальное уменьшение stdout не выдаются за доказательство provider-billed savings.
