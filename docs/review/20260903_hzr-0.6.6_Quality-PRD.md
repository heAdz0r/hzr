## 2. Корректность связки hook → daemon → fork-core → ledger

### F1 (Critical). Receipts хук-пути не дренируются

**Evidence.**

| Дата | Строк ledger | из них `rtk/*` producer | `sh` (raw proxy) | bypassed |
|------|-------------:|------------------------:|-----------------:|---------:|
| 08-25 | 6 419 | 5 790 | 31 | 435 |
| 08-26 | 5 579 | 5 281 | 782 | 1 031 |
| 08-27 | 5 682 | 4 847 | 374 | 541 |
| **08-28 (release 0.6.6)** | 11 | 8 | 4 | 5 |
| 08-29 … 09-03 | 7–165/день | **0** | **0** | **0** |

- Последняя `sh`-строка: `2026-08-28T00:04:20Z`. Первый недренированный journal: `Aug 28 03:05`.
- В `fork/`: 2 790 файлов `accounting-receipts-<corr>.jsonl` (+ `.lock`), 16 МБ, один engine-manifest
  `e4c0cfbe…` (текущий, не mismatch). Роуты внутри: 952 optimized, **1 838 bypassed**; delivered 6.37M токенов.
- В этой сессии: ~40 Bash-вызовов → 7 строк ledger (5 search + 2 memory, все через daemon).
  Stop-scorecard: «Measured commands 2, Saved 0».
- `git log -S HZR_INTERNAL_ACCOUNTING_RECEIPT_JOURNAL` → единственный коммит `28a594c release: hzr 0.6.6`.

**Механизм.** Хук экспортирует `HZR_INTERNAL_ACCOUNTING_RECEIPT_JOURNAL=fork/accounting-receipts-<corr>.jsonl`;
fork-core в `receipt_mode()` (`tracking.rs:1739-1815`) пишет receipt в этот файл вместо ledger.
Единственный потребитель — `drain_accounting(handle)` (`hzr-exec/src/accounting.rs:58`), вызываемый
из `api.rs:2756` **только в daemon-пути `exec/run`** и **только для handle этой корреляции**.
Для команд, которые выполняет хост (Claude Code) после `allow`, дренаж не вызывает никто:
в `hook_runner.rs` нет ни одного упоминания journal/receipt/correlation, в daemon нет sweeper'а,
маршрут `/v1/accounting/*` отсутствует (`server.rs` routes: health, engines, search, context, memory, exec/{rewrite,run,approval}, fidelity/reconcile, fork/run, codec, usage, billing, operations, policy, dashboard).

Changelog 0.6.6 утверждает: «accounting now crosses one typed receipt contract and is committed
idempotently by HZR's daemon-owned ledger writer». Верно только для `hzr exec run`.

**Почему тесты не поймали.** `smoke-install.sh` проверяет наличие хуков и dashboard, но нет ни одного
e2e-теста «dispatch → выполнить `updatedInput.command` → строка в ledger». Тестовые гейты зелёные.

**Варианты.**
- A. *Hook-side drain.* Новый endpoint `/v1/accounting/drain` (по списку correlation'ов сессии
  или по glob `fork/accounting-*-*.jsonl`); вызывать из `hooks dispatch` (следующий вызов дренирует
  предыдущие) и из `hooks feedback` (Stop). Плюс: нет фоновых процессов. Минус: последняя команда
  сессии дренируется только на Stop.
- B. *Daemon sweeper.* Периодический проход по `fork/` под lock с ack/удалением; интеграция с
  `AccountingCoverageStore` (открытый gap = число недренированных файлов). Плюс: ничего не теряется
  при падении хука. Минус: ещё один фоновый цикл в hzrd.
- C. *Engine → daemon напрямую.* fork-core постит receipt по loopback (токен уже в env), journal —
  fallback при недоступности daemon. Плюс: нулевая задержка, нет мусора на диске. Минус: изменение
  fork-core (parity docs, fork regression gate).
- Рекомендация: **B сейчас** (закрывает дыру и 16 МБ мусора без fork-изменений) + C в следующем минорном.

**Acceptance.** (1) Строки `rtk/*` producer снова ≥ 90% операций хук-канала за день. (2) Число
`accounting-receipts-*.jsonl` в `fork/` ≤ активных сессий. (3) `doctor` WARN «N undrained receipts»
при N > 0, PASS при 0. (4) Новый интеграционный тест: временный HOME + запущенный hzrd + `hooks dispatch`
→ `sh -c "$updatedInput"` → `select count(*) from commands where session_hash = …` = 1.
(5) Backfill 2 790 существующих receipts (или явное решение их отбросить с пометкой в ledger).

### F2 (High). Модель полноты учёта не знает о journals

`traffic_coverage.complete=false` и `coverage.live_complete=true` одновременно; причина —
`historical_complete=false` из-за 60 legacy degraded rewrites, а не из-за 2 790 живых пропусков.
Нужно: инвентарь journals → `AccountingCoverageStore` как открытый интервал `ForkProducer`;
`stats` печатает «N операций ожидают дренажа», `economic_claim_ready=false` пока N > 0.

### F3 (High). `find` passthrough без границ, учтён как optimized

`find_cmd.rs:176-197`: любой неподдерживаемый флаг (`-exec`, `-newer`, …) → `run_find_passthrough`
→ `FilterMode::Passthrough` без cap → `timer.track_passthrough(...)` записывает `rtk_cmd="rtk find … (passthrough)"`.
Ledger: `find` семейство 73 вызова, baseline 4 670 054 → delivered 4 658 330 (0.25%); один вызов —
4 620 135 токенов за 3.6 с. Семейство при этом в таблице «optimized / available».

Fix: (a) passthrough → `route=bypassed, measurement=unmeasured` (честный учёт); (b) cap вывода
passthrough тем же бюджетом, что у `read` (например 200 строк / 16 КБ) с recovery-подсказкой
(`HZR_RAW_FIDELITY=1 … reason=complete_log`); (c) поддержать `-exec`-less предикаты `-newer`, `-size`,
`-mtime` в нативном парсере, чтобы passthrough был редкостью.
Acceptance: `find . -newer x` → ≤ cap строк + строка «N omitted; recovery: …»; семейство `find`
в `stats` не показывает passthrough как optimized.

### F4 (High). `hzr read <file>` без флагов отдаёт весь файл

`hzr read crates/hzr-core/src/ledger.rs` → 286 351 байт (≈72K токенов) за 62 мс; файл 289 488 байт.
Default level `minimal` = strip blank/comments, **размерной границы нет**. Контракт обещает:
«Unbounded `read --level none` … is automatically reduced», «Uses the smart default». Нативный Read
ограничен 2 000 строками — hzr здесь хуже. `hzr read --help` не показывает ни одной опции (§F15).

Fix: бюджет по умолчанию (предложение: 400 строк или 12K токенов, что раньше); при превышении —
outline + первые N строк + строка recovery (`--from/--to`, `--level none` с `HZR_EXACT_FIDELITY`).
Учитывать в ledger как `read_budgeted` с `selection_avoided`. Acceptance: чтение файла > бюджета
без флагов ≤ 12K токенов; `read --outline` и диапазоны не меняются; тест на 6K-строчном фикстуре.

### F5 (Medium). Самовызов `hzr …` — через `rtk proxy /bin/sh -c`

`rewrite-plan 'hzr stats --since 7d'` → `decision=proxy, class=e10_capability_gap`. Выполняется как
`rtk proxy /bin/sh -c 'hzr stats …'` (лишний процесс + шелл), учитывается семейством `sh`
с рецептом «no HZR filter yet; use hzr exec run» — то есть рекомендация обернуть hzr в hzr.
`hzr exec run "cargo build 2>&1 | tail -5"` тоже e10/proxy. Для compound-shell (`for …; do …; done`)
класс e5 `avoidable=true`, а «правильный» `hzr exec run 'for …'` даёт e10 `avoidable=false` при
нулевой фильтрации — accounting поощряет церемонию без пользы.

Fix: (a) `hzr` как first-class префикс в `hzr-core/operation.rs` → `allow raw` с attribution
`hzr_native`, не в bypass; (b) рецепт для `sh`-семейства без фильтра: не «use hzr exec run», а
конкретный первоклассный маршрут, если он есть, иначе молчание; (c) `avoidable` для e5 только если
существует эквивалент с фильтром (сейчас `for`-цикл наказывается без альтернативы).

### F6 (Medium). Два SessionStart-хука

`~/.claude/settings.json`: `init --if-needed --quiet` **и** `init --if-needed --quiet --session-start-hook`.
`adoption.rs:320-331` `matches()` узнаёт только суффиксы с `--session-start-hook`, поэтому legacy
запись не признана своей, не заменена, а новая добавлена рядом. Каждая сессия — двойной `init`
(~720 байт вывода × 2 и двойная транзакция). Fix: legacy-суффикс в список + миграция при `install`;
`doctor` check «duplicate hook owners». Acceptance: после `hzr install` ровно один SessionStart.

### F7 (Medium). Ложный WARN `degraded_rewrites`

`diagnostics.rs:1601-1609`: третья ветка (`Ok(coverage)` при `!complete`) печатает
`unreconciled_rewrites` = 0 как WARN, потому что `complete=false` из-за `historical_complete`.
Fix: WARN только при `unreconciled_rewrites > 0`; историческую неполноту — в detail PASS-строки.

### F8 (High, безопасность данных пользователя). Тест пишет в реальный конфиг Claude Desktop

`~/Library/Application Support/Claude/claude_desktop_config.json`, mtime `Sep 3 12:33:59`:
`{"command":"/Users/andrew/Programming/hzr/target/debug/hzr","args":["mcp","serve","--workspace",
"/private/var/folders/…/T/tmp.FeSav6W6BQ/repo"]}`. `tmp.XXXXXXXXXX` — шаблон `mktemp` из
`smoke-install.sh` (`HZR_SMOKE_TEMP`). `default_paths()` (`client_config.rs:310-322`) берёт HOME через
`BaseDirs`, override — только `CLAUDE_DESKTOP_CONFIG`. Значит существует путь запуска (шаг `smoke-install.sh` или
локальный `hzr release`; полный `cargo test` исключён — см. §8), где ни HOME, ни
`CLAUDE_DESKTOP_CONFIG` не запинены. `doctor` это видит
(WARN `client_mcp_workspace`), но предлагает «select this workspace», хотя workspace не существует.

Fix: (a) найти вызов (grep `mcp config … --apply` в тестах/скриптах, прогнать `cargo test` с
`HOME` read-only); (b) защита: `client_config::apply` отказывает, если target-путь лежит вне
`$HOME`-песочницы теста **или** бинарь — `target/debug/*` без `HZR_ALLOW_DEV_CLIENT_WRITE=1`;
(c) `doctor`: если workspace регистрации не существует — remediation «remove/repin», а не «select».
Acceptance: полный `cargo test --workspace` + `smoke-install.sh` не меняют mtime реальных клиентских конфигов (проверка в CI: snapshot до/после).

### F9 (Medium). Глобальная MCP-регистрация запинена на один проект

`~/.claude.json → mcpServers.hzr.args = ["mcp","serve","--workspace","/Users/andrew/Programming/anonymous_bot"]`;
per-project регистрации есть у 5 проектов. Контракт: «never use an MCP session bound to another
workspace». Итог: в hzr-репо (и в большинстве других) MCP-инструменты формально запрещены →
`traffic_coverage.by_channel.mcp = 10` за 7 дней против 4 405 hook_cli. Инвестиции в MCP-слой
(`hzr_context_plan`, `hzr_memory_*`, `hzr_codec`) не окупаются, потому что канал недоступен.

Fix: `mcp serve` без `--workspace` должен привязываться к workspace клиента: `roots` из MCP
`initialize`, затем `$CLAUDE_PROJECT_DIR`, затем cwd с отказом от `/` и `$HOME` (как в
`classify_workspace_binding`). Глобальную регистрацию — без pin; `doctor` предупреждает о
глобальном pin на конкретный проект. Acceptance: один глобальный `mcpServers.hzr`, `initialize`
в любом репо возвращает `workspace.bound=true` с его корнем.

### F10 (Medium). Память: границы и гигиена scope

- `hzr memory recall "pianomarvel"` из hzr-репо возвращает `context-pianomarvel-…e347808b` и
  `decisions-pianomarvel-…e347808b` (22–23.08) — тот же namespace-хэш, что у `context-hzr-…e347808b`.
  Это **project-namespace hzr**, а не global: сессия по pianomarvel писала память с привязкой к
  workspace hzr (глобальный MCP-pin или cwd — см. F9). Контракт «another repository's memory is never
  reachable» нарушен на уровне записи, а не чтения. Guard на store по содержимому/пути отсутствует
  (`api.rs:1724` только формирует topic по переданному project).
- Payload: ~2.5 КБ на память; `--limit 10` ≈ 25 КБ ≈ 6K токенов на один recall.
- `memory status`: «FTS5 retrieval; embeddings are disabled» — recall лексический.
- Использование: 3 recall / 7 дней, `memory_store` в by_mode отсутствует.

Fix: (a) store в global scope принимает только topics `preferences|user-*|architecture-global`
и отклоняет содержимое с именем текущего/другого проекта; (b) recall по умолчанию — компактные
строки `id · topic · summary(140)` + `--expand <id>`; (c) решить про embeddings (стоимость vs польза)
или явно задокументировать FTS-only в контракте.

### F11 (Medium). Тройная инъекция контракта и противоречия инструкций

Размеры: `~/.claude/CLAUDE.md` 13 991 Б (managed-регион 6 838 Б), `/Users/andrew/CLAUDE.md` 6 904 Б,
`<repo>/CLAUDE.md` 6 904 Б. Claude Code загружает все три → ≈ 20 КБ ≈ 5K токенов на сессию, из них
две трети — дубликат. Причина: `hzr init` был выполнен с cwd=`$HOME` (Claude Desktop стартует из
домашнего каталога) и создал «workspace instructions» для HOME; `instructions.rs` не проверяет
корень на `/`, `$HOME` (в отличие от `mcp.rs:145 classify_workspace_binding`).
Дополнительно пользовательский CLAUDE.md содержит два поколения директив: `hzr rtk -- read/write` (5)
против `hzr read/write` (7) и устаревшее «PreToolUse matcher is Bash|Agent|Task only» (matcher уже
`Bash|Agent|Task|Read|Grep|Glob|Edit|Write`). `doctor` ловит такие противоречия только во fleet-файлах
(`fleet_instruction_exemptions`), но не в `~/.claude/CLAUDE.md`.

Fix: (a) `init`/`enable` отказывают от `$HOME` и `/` как workspace; (b) managed-регион пишется один раз
в ближайший applicable файл, если предок уже содержит идентичный регион — placement `inherited`;
(c) `doctor` check `user_instruction_conflicts` для legacy `hzr rtk -- read|write` и stale-утверждений.
Acceptance: в сессии из репо ровно один managed-регион; `/Users/andrew/CLAUDE.md` удалён или сведён к ссылке.

### F12 (Low). `.rtk-lock` в снапшоте fork-core

`git ls-files | grep -c rtk-lock` = 50 (все внутри `fork-core/rtk`, размер 0, hash `e3b0c442…`
в `CURRENT_SHA256SUMS`, `SHA256SUMS`, `FORK_FILES`, `CURRENT_FILES`). Ещё ~20 untracked в корне и `docs/`
(gitignore закрывает, но `TEST_DEBT_0.6.*.md.rtk-lock` остались без оригиналов). Fix: `write_lock.rs`
удаляет lock после успешной записи; исключить `*.rtk-lock` из снапшот-скриптов; `git rm` + перегенерация сумм.

### F13 (High, truthfulness). Baseline и delivered не знают о хостовом усечении

Claude Code не отдаёт модели вывод инструмента целиком: большой результат сохраняется в файл и
показывается превью (~2 КБ) — это наблюдается в текущей сессии (`Output too large (44.3KB)… Preview
(first 2KB)`). Следствия для ledger:
- `grep>search` 126 вызовов: baseline 13 162 788 → delivered 12 870 — «сэкономлено» 13.15M из 17.01M
  net (77% headline «USD 85.05»). Без HZR модель увидела бы не 13M токенов, а хостовый cap.
- `find` 4.62M delivered одним вызовом — модель этого тоже не видела.
