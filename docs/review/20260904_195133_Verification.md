Первый полный gate последовательно прошёл этапы до fork-теста: `scripts/complete-gate.sh:20-23` ставит fmt, workspace clippy и workspace tests перед `verify-fork-core.sh --test`. Поэтому их успешное завершение в этом запуске следует из управления скриптом. Отдельного полного нефильтрованного отчёта с числом workspace-тестов в этом запуске не сохранилось; не подменяем его частичными 387 тестами последующего запуска.

Для изолированного target использовалось:

~~~sh
hzr exec run 'env -u HZR_INTERNAL_ACCOUNTING_RECEIPT_JOURNAL -u HZR_INTERNAL_ACCOUNTING_FAILURE_JOURNAL -u HZR_INTERNAL_ACCOUNTING_CORRELATION -u RTK_TRACKING_DISABLED cargo test --manifest-path fork-core/rtk/Cargo.toml --test internal_env'
~~~

Точное падение: `fork-core/rtk/tests/internal_env.rs:46`, `no such table: commands`. Тест задаёт локальную `RTK_DB_PATH`, но inherited receipt mode направляет запись в journal. Исправлять нужно изоляцию fixture и отдельно проверять оба режима. Код теста в рамках аудита не изменён.

## Свежие воспроизведения поведения

- `hzr search "drain accounting receipt journal after producer crash" --mode semantic --path crates --limit 5 --json`: реальный маршрут `fork_rgai_grepai`; неверные `crates/crates/...`; проверка существования первого пути отрицательная.
- `hzr context plan "sweep_once accounting receipts" --path crates/hzr-daemon --memory-limit 1 --search-limit 5 --json`: смешение workspace-relative и scope-relative ссылок; четыре из пяти outlines недоступны. Содержимое возвращённой памяти не использовалось для выводов.
- Полный 299-строчный `accounting_sweeper.rs` в одном bounded exact read: 11000 bytes stdout+stderr; три диапазона того же файла: 11272 bytes. Это +272 bytes / +2.47% и два лишних вызова; не измерение billed tokens.
- Новый pinned CLI MCP stdio probe: initialize и tools/list; 13 tools, 25574 bytes компактного tools array и 25584 bytes объекта `{"tools":...}`. Это не доказательство binding уже зарегистрированного MCP-сеанса приложения.
- Doctor: installed component hashes verified; ICM ready/FTS5; semantic engine реально используется. Одновременно accounting gaps и старые осиротевшие smoke ICM. Сводный `healthy=true` не является end-to-end проверкой.
- Fleet: 94 зарегистрированных пути, 85 успешных запросов, 83 нулевых, 9 отсутствующих. Сумма двух активных проектов совпадает с frozen global. Подробности и границы — в [fleet audit](20260904_195133_Fleet-Usage-7d.md).

## Что не проверено

- Billed task savings, качество реальных ответов и paid paired model evaluation: новых платных вызовов не делали.
- Реальная замена tool output в установленном Claude/Codex: изучены текущие официальные контракты, но не менялись пользовательские hooks/config и не выполнялся trusted-host sentinel.
- Полный source gate после исправления среды: исправление ещё не реализовано.
- Release/install/platform matrix, Windows/Linux и деградация ICM при живом зависшем процессе: не заявляются прошедшими.
- Существующие процессы не завершались; reconciliation выполнялся только как диагностика/dry-run.
- Privacy-safe агрегаты не позволяют восстановить intent, необходимость полного файла, фактические native bypasses или причинность повторов.
