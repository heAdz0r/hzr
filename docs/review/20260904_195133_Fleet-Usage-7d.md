# Независимый аудит HZR по всем зарегистрированным проектам за последние 7 дней

Дата: 2026-09-04. Анализ текущего кода и живых агрегатов. Старые PRD не использовались. Реализация и настройки не менялись.

## Вердикт

Текущие данные подтверждают отдельные полезные сокращения результатов, но не доказывают экономию полного агентского сеанса или сохранение качества решения. Почти вся положительная оценка приходится на разработку самого HZR. Во втором наблюдаемом проекте эффект мал и исчезает в пессимистическом сценарии повторных запросов. Маркировка маршрута `optimized` сама по себе не означает полезную экономию.

Нельзя по этим данным утверждать, что остальные проекты не используют инструменты: их наблюдаемый ledger пуст, а полнота перехвата не доказана. Нельзя также приписывать всю долю `raw` обходам со стороны LLM: разрешенный passthrough, корректное точное чтение, unsupported команды и ошибки классификации смешиваются.

## Точные проблемные места

### FLEET-1. Разные команды exec объединены в other — приоритет P1

`crates/hzr-core/src/ledger.rs:3275-3281` выбирает family из `detail.operation.as_str()`, если typed detail существует, перекрывая результат `classify_operation(recorded_command)`. В `privacy_safe_family` (884-892) есть безопасные git/cargo/gh/docker/python/bun/npm, но нет exec/context. Поэтому typed exec становится other.

Следствие: нельзя выяснить, какие команды среди 453 raw exec чаще требуют адаптера fork-core/rtk. Статистика `--all` дает все агрегатные группы, а не реальные command argv. Более строгая инструкция «используй эффективные команды» этот пробел не исправляет.

Требование: разделить неизменяемые operation_kind и executable_family. Хранить allowlisted executable + adapter ID/version + plan decision + fallback reason. Аргументы, пути, вывод и query text не нужны для такого анализа. В отчете отдельно отражать supported_adapter, typed_passthrough, unsupported, fidelity_exact, semantic_pipeline_unsafe.

### FLEET-2. Rerun tax не доказывает причиненный фильтром ущерб — P1

`ledger.rs:2563-2610` выбирает совпадение command_hash и session_hash в пределах следующих 8 measured строк после optimized вызова с output < input. Hash строится из original_command и recorded_command (`ledger.rs:3292-3295`).

Нет учета версии файла, изменившегося репозитория, намерения, elapsed time, принятого ответа и логического operation ID. В запросе нет исключения accounting_stage, поэтому стадии одного логического действия потенциально могут загрязнять sequence; это риск алгоритма, не доказанная причина конкретных 40 строк. Новая синтаксическая форма той же потребности, другой диапазон файла или иной search query также не будут считаться повтором.

`stats.rs:221-227` прямо признает другие причины повторов и называет after-rerun pessimistic reading. Поэтому -21129 в anonymous_bot — диагностический сигнал, не измеренная отрицательная экономия.

Требование: пользовательская метрика «observed repeated retrieval», отдельно подтвержденная filter-induced recovery; operation lineage, artifact revision hash, content-region overlap и logical stage dedup. Различать повтор после изменения и повтор для восстановления недостающего контекста. Тесты должны включать оба случая и разные выражения одной потребности.

### FLEET-3. Глобальная картина наблюдения неполна — P0

Frozen traffic_coverage: accounted 660 / observed 688 (95.930%), native_unaccounted = 0, unmeasured_bypass = 28, complete=false, completeness=degraded_rewrite_gap. Ноль native_unaccounted не показывает, что все native calls перехвачены.

Каналы: hook_cli 681, MCP 7. hook_cli объединяет происхождение, поэтому эти цифры не показывают соотношение Codex и Claude Code или фактическое использование native MCP в каждом host. Отдельного by_host в CLI report нет. Host-visible estimate incomplete; 414 операций без validated cap. Provider usage и task outcomes не собраны.

В frozen global healthy coverage имеются исторические пропуски, которые не ограничены project/time window: сами notes stats явно предупреждают об этом. Их нельзя назвать «ровно столько потеряно за последние 7 дней в этом проекте».

Требование: producer receipt delivery + durable reconciliation; отдельные host/channel/stage и unknown denominator; количество наблюдаемых и ожидаемых событий; bounded per-project/per-host daily export с фиксированными since/until. Ready runtime и полное accounting должны оставаться разными статусами.

### FLEET-4. Fleet history невозможно удобно анализировать — P1

`hzr activation status --json` возвращает mode=all, enabled_workspaces=[], что не перечисляет runtime projects. Чтобы построить отчет, пришлось извлечь inventory через doctor dry-run и вызвать stats 94 раза. Девять удаленных worktree имеют историю регистрации, но stats требует существующий directory. Это мешает историческому аудиту удаленных checkouts.

Требование: `hzr stats --group-by project,host,family --since ... --until ...` либо typed read-only report endpoint. Принимать исторический workspace ID без требования существующего cwd. Включать deleted/inactive в отчет, не восстанавливая их и не меняя registry. Один атомарный snapshot, bounded pagination, aggregate totals и экспорт безопасных данных.

### FLEET-5. Не оптимизировать tail/full-file по одной длине — P1

370138 estimated tokens в 38 read_tail важны для приоритизации, но агрегаты не показывают что читалось: файл, лог, содержимое или восстановление недостающих фрагментов. Нельзя из названия режима заключить, что LLM неоправданно читала полные файлы. Нужно проверить цепочки, а не вводить новый запрет.

Требование: для retrieval сохранить privacy-safe artifact identity, revision, source bytes, selected regions, delivered bytes, truncation, cursor, logical operation ID. Дедупликация уже доставленных областей должна быть локальной сессии и версии документа. Полный exact read автоматически допустим, когда прогноз суммарной стоимости дальнейших диапазонов выше одного полного чтения или файл является обязательным целостным входом.

### FLEET-6. Диагностика сама бывает дорогой — P2

Doctor fleet dry-run вернул около 21841 output tokens в первом tool result, список многократно повторяющихся global rewrite previews и больше 2500 JSON lines. Для получения только проектов пришлось повторять запуск с jq. Это непосредственный пример «короткий вопрос -> большой внутренний документ -> повторный запрос».

Требование: отдельный inventory endpoint и компактный default doctor; detailed evidence за handle. В dry-run дедуплицировать идентичные global targets. Нельзя предписывать каждый раз полный doctor, если нужен один project list.

При первом fleet dry-run были transient ошибки claude_instructions и codex_instructions:
- `/Users/andrew/.claude/CLAUDE.md: HZR contract block is absent; run \`hzr init --if-needed\``
- `/Users/andrew/.codex/AGENTS.md: HZR contract block is absent; run \`hzr init --if-needed\``

При повторе той же команды в 19:53:20 UTC они отсутствовали; preview_changes=false, только 9 absent workspace errors оставались. Аудит конфигурацию не менял. Причина транзитного расхождения не установлена; не используем это как доказательство постоянной поломки global instructions.

## Что доработать для полезной экономии

1. Сначала исправить достоверность учета и экспорт. Без этого невозможно выбрать выгодный адаптер и невозможно сравнить инструменты честно.
2. Минимизировать общую стоимость retrieval episode, а не длину каждого ответа. Эпизод должен включать plan, tool args/schema, результаты, follow-ups, повторные регионы, codec, error/retry и финальный контекст модели.
3. Для известного literal — compact exact search без большого JSON envelope. Для конкретного пути/символа — прямой bounded read/symbol. Semantic/context plan — для неясного местоположения и архитектурных вопросов, с измерением полезности найденных доказательств.
4. Когда информации достаточно, не предписывать новые вызовы. Когда целый файл дешевле нескольких passes — вернуть целый файл с явной cost rationale, без трактовки корректного чтения как нарушения.
5. Для exec адаптер выбирать по AST команды, окружению и смыслу вывода. Сохранять shell grammar и не пропускать бинарные данные/JSON/patch через prose filter. Если полезного фильтра нет — typed passthrough, а не цепочка отказов с тем же полным выводом в конце.
6. Для больших test/build/log output: сначала короткий status + failures + evidence handle, затем выборочный retrieval. Для короткого полного вывода дополнительная оболочка не должна делать его дороже.
7. Проверить одинаковые реальные задачи на HZR, native baseline и упрощенном HZR. Стратифицировать по проектам и стеку; self-development HZR не должен доминировать. Измерять task success, проверенные ошибки, время, число tool calls, repeat/overlap, actual provider usage при наличии и cached/uncached отдельно.

## Приемка следующего этапа

- На детерминированном multi-host corpus каждая логическая доставка имеет ровно один receipt; replay и crash не теряют события и не удваивают credit.
- Multi-project report воспроизводим с фиксированным cutoff; сумма непересекающихся проектов соответствует global, deleted workspace query поддерживается.
- Все exec строки с известным бинарником имеют проверенный family и adapter/fallback reason; generic other остается только для действительно неизвестного.
- Zero, negative, unavailable и unknown показываются отдельно. Optimized route с большим output не может рекламироваться как savings.
- Sequential small reads vs single full read сравниваются по совокупному episode cost; разрешается full read при меньшей ожидаемой стоимости или требованиях точности.
- Метрика полезности валидируется accepted-task evidence и meaningful tests. Биллинг не выводится из bytes/4.
- Численные цели по экономии фиксируются после независимого baseline corpus; текущие 9.565% не использовать как подтвержденный SoTA результат.

## Что проверено и что не проверено

Проверены текущая typed aggregation logic, source rerun heuristic, 94 project stats calls, dry-run fleet inventory и арифметическая сверка двух активных проектов с frozen global. Отказы отсутствующих путей указаны явно. Production config и engine stores не менялись.

Полный cargo gate независимо ведет основной аудит; этот субагент его не запускал. Не выполнено причинное replay сравнение задач, не восстановлены raw argv и tool outputs, не доказана конкретная потеря смысла в исторических командах, не подтвержден provider-billed эффект. Это ограничения имеющихся данных и текущего API, а не положительные результаты проверки.
