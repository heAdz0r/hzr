# Производительность и масштабирование HZR: новый аудит

Дата: 2026-09-04. HZR 0.7.1, commit `fbf204d48704160407e3f06035ac32b9cf0bc67a`.
Это внутренний отчёт. Нагрузочный benchmark и эксперимент с billed LLM tasks не выполнялись.

## Главный вывод

Основное ограничение сейчас — полезность и целостность маршрута, а не доказанный недостаток CPU. Неправильный путь, потерянная причина теста или лишний цикл Read → denial → retry способны уничтожить выигрыш от уменьшенного текста. Сначала нужно измерять полную retrieval episode и cost per accepted task.

## Backend и хранение

**Receipt lifecycle.** Sweep читает registry contexts, а inventory находит orphan journals без contexts. Дополнительное ускорение sweep не восстановит потерянную ownership-связь. Сначала durable registration, idempotency, commit-before-ack и bounded quarantine; затем нагрузочная проверка growing backlog.

**Context planner.** Outlines вызываются последовательно; бюджет смешивает стоимость будущего полного файла с текущим выдаваемым evidence. Нужны batch outline, cache по source hash/index generation, отдельные delivery и expansion costs. Параллельность должна быть ограничена, чтобы не запускать subprocess на каждый hit.

**ICM.** FTS5 работает без embeddings. Это допустимый режим, не автоматический дефект. Полезность semantic memory нужно измерять ablation; mandatory recall на каждом запросе может тратить больше, чем возвращает. Центральное владение снижает дублирование, но не заменяет проверку restart/shutdown.

**grepai.** В `crates/hzr-core/src/config.rs:374-375` default watcher limit8 и idle TTL15мин. Это ресурсная политика, а не обещание пропускной способности. Стоимость индекса зависит от объёма кода, модели embeddings, churn и warm/cold state.

**Ledger.** Текущая классификация exec → other не позволяет выделить дорогие command families. Отдельно хранить operation_kind и privacy-safe executable family, host/version, stable project ID, snapshot window, task/episode IDs. Raw argv и source content для этого не нужны.

## Масштабирование: 3, 100, 1000 пользователей

HZR — локальный control plane. Сто пользователей на ста компьютерах не эквивалентны ста одновременным агентам одного daemon. Ниже сценарные риски, не прогноз измеренной ёмкости.

| Сценарий | 3 пользователя | 100 пользователей | 1000 пользователей | Что проверить |
| --- | --- | --- | --- | --- |
| Один независимый workstation на пользователя | Три независимых локальных store | Сто независимых store | Тысяча независимых store | Версии, миграции, доставка bundle, opt-in privacy-safe telemetry |
| Несколько агентов на одном host | Уже важны job handles и cancellation | Нет доказанной ёмкости; contention вероятен | Такая централизация не является подтверждённой архитектурой | Mixed concurrent workloads, admission control, CPU/RSS/FD/queue latency |
| Активные worktrees на одном host | Могут помещаться в watcher limit8 | Eviction/cold-start; bounded watcher budget | Значительная очередь и churn без дополнительных политик | LRU/TTL fairness, index generation, cold vs warm latency |
| Historical fleet reporting | Несколько stats roundtrips | O(N) клиентских запросов неудобно | Текущий per-cwd API непригоден для обзора | Один paginated snapshot по stable project IDs, включая удалённые cwd |
| Process lifecycle defects | Небольшой, но реальный orphan leak | Повторяемые installs/tests накапливают children | Без cleanup риск эксплуатационно неприемлем | Owned process groups, SIGTERM/INT, crash detection, bounded backoff |
| LLM economics | Достаточно для пилота correctness | Возможна репрезентативная выборка задач | Нужна статистическая стратификация | Accepted outcomes, host coverage, paired request receipts |

Нельзя корректно написать «выдержит 1000 пользователей», умножив один замер памяти или количество процессов. В этом аудите throughput/p50/p95/RSS под нагрузкой не измерены.

## Frontend

Доработка visualizer отдельно разрешена пользователем. До неё UI нельзя использовать как доказательство экономии: красивый percentage поверх неполного ledger сохраняет неверную интерпретацию.

Требования к UI: быстрый выбор проекта, короткий обзор состояния, различение estimates и provider evidence, видимая свежесть/ошибка, осмысленные фильтры активности, progressive disclosure подробностей, responsive layout и keyboard access. Результаты bundle/typecheck/visual QA должны находиться в [дизайн-отчёте](../review/20260904_UI-Design.md); здесь они заранее не объявляются прошедшими.

## Приоритеты и измерения

1. P0: paths, receipts, long execution, error preservation — предотвращают повторную работу.
2. P1: batch/expand/cost-aware full read и MCP parity — снижают число диалоговых roundtrips.
3. P1: task receipts и safe command families — дают основание выбирать RTK-оптимизации.
4. P1: pinned host interception — уменьшает output до попадания в контекст с проверкой реальной доставки.
5. P2: calibrated retrieval и selective memory — только после оценки marginal utility.

Для каждого изменения измерять warm/cold latency, p50/p95, peak RSS, job concurrency, bytes и tokenizer counts, total provider usage, retries, accepted-task quality. Базовый агент обязан использовать разумные native search/read, иначе сравнение будет искусственным.

Целевой эксперимент и критерии допуска описаны в [PRD](../prd/20260904_AGENT_EFFICIENCY.md). Числа ≥15% median task-token reduction и ≤50ms p95 interception overhead в нём — предлагаемые цели, не текущие результаты.
